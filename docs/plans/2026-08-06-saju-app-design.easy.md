# 사주 앱 설계안 — 쉬운 버전

> 자세한 기술 버전: [원문](./2026-08-06-saju-app-design.md)
> 이 문서는 사주도 개발도 처음인 사람을 위한 풀어쓴 버전입니다. 결론과 수치는 원문과 같습니다.

## 한 줄 요약

**생년월일시를 넣으면 사주 여덟 글자를 계산하고 풀이를 보여주는 웹사이트를, 작은 기능 하나를 끝까지 완성해 가며 공부하듯 만든다.**

---

## 1. 이게 뭘 만드는 프로젝트야?

사주는 태어난 **연·월·일·시** 네 가지를 각각 두 글자(예: `을해`)로 바꾼 것입니다.
4개 × 2글자 = **8글자**라서 "사주팔자(四柱八字)"라고 부릅니다. 네 개의 기둥(柱)과 여덟 글자(字)라는 뜻이에요.

이 앱이 하는 일은 두 단계입니다.

1. **계산** — 생년월일시를 8글자로 바꾼다
2. **풀이** — 그 8글자를 보고 "이런 성격, 이런 재물운" 같은 설명을 보여준다

목표는 두 가지입니다.

- 실제로 **출시할 수 있는 제품**을 만든다
- 그 과정에서 **하나씩 배운다** (특히 모노레포와 NestJS는 처음이라 배우면서 진행)

### 어떤 순서로 만들까? — "수직 슬라이스"

> 🏣 **비유: 케이크를 자르는 방법**
> 케이크를 층별로 만들면(빵 다 굽고 → 크림 다 바르고 → 장식 다 하고) 마지막까지 한 조각도 먹어볼 수 없습니다.
> 대신 **얇게 한 조각을 세로로 잘라** 빵·크림·장식이 다 있는 조각을 먼저 완성하면, 처음부터 "맛"을 볼 수 있어요.

이 프로젝트도 그렇게 합니다. 기능은 아주 적게, 하지만 그 기능이 **화면 → 서버 → 데이터베이스 → 로그인**까지 전부 거치도록 만듭니다. 그래야 전체 구조를 일찍 몸으로 익힐 수 있어요.

---

## 2. 전체 구조는 어떻게 생겼어?

### 큰 그림

```
saju-app/  (저장소 하나에 전부 들어 있음)
├── packages/core/   ← 사주 계산기 (두뇌)
├── apps/api/        ← 서버 (계산기를 대신 돌려주는 창구)
└── apps/web/        ← 웹사이트 (사람이 보는 화면)
```

| 부분 | 하는 일 | 비유 |
|------|---------|------|
| `core` (엔진) | 생년월일 → 8글자 계산, 풀이 조립 | 식당의 **레시피** |
| `api` (백엔드) | 웹사이트의 요청을 받아 엔진을 돌리고 결과를 돌려줌. 로그인·저장 담당 | **주방** |
| `web` (프론트) | 입력 화면과 결과 화면을 보여줌 | **홀(손님 자리)** |

손님(web)은 주문만 하고, 요리는 주방(api)이 레시피(core)대로 합니다.
레시피를 따로 떼어놨기 때문에 나중에 **모바일 앱**을 만들어도 같은 레시피를 그대로 쓸 수 있어요. 화면만 새로 만들면 됩니다.

### 왜 한 저장소에 다 넣어? — 모노레포

> 🏣 **비유: 한 집에 사는 가족**
> 앱 세 개를 저장소 세 개로 나누면 따로 사는 가족이라, 물건(코드)을 빌리려면 택배를 보내야 합니다.
> 한 저장소에 넣으면(**모노레포**) 한 집에 사는 것처럼 바로 꺼내 쓸 수 있어요.

- **yarn workspaces**: 집 안의 방들을 서로 연결해 주는 배선
- **Turborepo**: 집안일(빌드·검사·테스트)을 순서대로, 빠르게, 동시에 처리해 주는 **살림 매니저**. 이미 한 일은 기억했다가 다시 하지 않습니다(캐싱).

## 3. 어떤 도구를 쓰는데?

전부 **TypeScript** 한 가지 언어로 씁니다. JavaScript에 "이 값은 숫자다, 이건 글자다" 같은 꼬리표(타입)를 붙인 언어라 실수를 미리 잡아줍니다.

| 영역 | 도구 | 쉽게 말하면 |
|------|------|-------------|
| 저장소 관리 | Turborepo + yarn | 위의 "살림 매니저 + 배선" |
| 엔진 | 순수 TypeScript | 다른 도구에 기대지 않는 계산기 |
| 서버 | **NestJS** (REST 방식) | 서버를 정해진 틀대로 깔끔하게 짜게 해주는 도구 |
| 로그인 | Passport + JWT (카카오·구글) | 카카오·구글로 로그인하고, 로그인했다는 **출입증(JWT)** 을 발급 |
| 화면 | **Next.js** + Tailwind CSS | 웹사이트를 만드는 도구 + 디자인을 빠르게 입히는 도구 |
| 데이터 저장 | **PostgreSQL** + Prisma | 데이터를 담는 창고 + 창고를 코드로 편하게 다루는 도구 |
| 테스트 | **Vitest** | 계산이 맞는지 자동으로 확인 |
| 배포 | 화면=Vercel / 서버=미정 | 인터넷에 올리는 곳 |

> 💡 **"REST"와 "GraphQL"이 뭐야?** 화면이 서버에 데이터를 달라고 요청하는 방식입니다.
> REST는 "메뉴판에 있는 걸 시키는" 방식, GraphQL은 "원하는 재료만 골라 주문하는" 방식이에요.
> 처음엔 더 단순한 REST로 하고, GraphQL은 손에 익은 뒤 배웁니다.

### 데이터 창고는 어디에?

- **지금(개발 중)**: 내 컴퓨터에 **Docker**로 PostgreSQL을 띄웁니다. Docker는 프로그램을 "상자"에 담아 켜고 끄는 도구예요. `docker compose up -d`로 켜고 `down`으로 끕니다. 꺼도 데이터는 남아요.
- **나중(출시)**: 아마존 클라우드(**AWS RDS**)로 옮깁니다.
- 옮기는 방법은 **창고 주소(`DATABASE_URL`) 하나만 바꾸면 끝**입니다. 둘 다 같은 PostgreSQL이라 코드를 고칠 필요가 없어요.

## 4. 어떤 정보를 저장해?

> 💡 **핵심: 계산 결과는 저장하지 않는다. 입력값만 저장한다.**

8글자 같은 계산 결과는 같은 입력이면 **항상 같은 답**이 나옵니다. 그러니 저장할 필요 없이 볼 때마다 다시 계산하면 돼요.
저장해 두면 나중에 계산 방식을 고쳤을 때 **옛날 결과가 그대로 남는 문제**(stale, 낡은 데이터)가 생깁니다.

| 저장하는 것 | 들어가는 내용 |
|-------------|---------------|
| **사용자** (User) | 이메일, 이름, 어디로 로그인했는지(카카오/구글) |
| **사주 프로필** (SajuProfile) | 별명, 성별, 양력/음력, 생년월일, 태어난 시각(모르면 비워둠), 윤달 여부, 태어난 곳의 경도 |

- 한 사람이 **본인 + 가족·친구·연인** 여러 명의 사주를 저장할 수 있습니다.
- 풀이 문장들은 창고(DB)가 아니라 **코드 안의 글 파일**로 관리합니다.

## 5. 사주 계산기(엔진)는 어떻게 만들어?

### 직접 만든다

간단한 규칙은 **직접 짭니다.** 다만 천문학 계산(해의 위치, 음력 변환)처럼 어려운 부분만 검증된 도구를 빌려 씁니다.

그리고 이미 있는 사주 라이브러리 하나(`lunar-javascript`)를 **정답지**로 옆에 두고, 우리 계산과 맞는지 자동 테스트로 비교합니다.
막히면 그때 라이브러리를 통째로 쓰는 쪽으로 바꿉니다.

### 넣는 것과 나오는 것

| 넣는 것 | 나오는 것 |
|---------|-----------|
| 양력/음력, 생년월일, 시각(선택), 성별, 윤달 여부, 경도 | ① **8글자** (연·월·일·시 기둥) |
| | ② **일간** — 태어난 날의 앞글자. 사주에서 "나 자신"을 뜻함 |
| | ③ **오행 분포** — 나무·불·흙·쇠·물(목화토금수)이 각각 몇 개인지 |
| | ④ **십성** — 다른 글자들이 "나"와 어떤 관계인지 (10종류) |
| | ⑤ **신강/신약** — "나"의 기운이 센지 약한지 |

결과를 이렇게 **항목별로 나눠서** 내놓는 이유는 6장에서 나옵니다.

### 정확도를 한 층씩 쌓는다

쉬운 것부터 하나씩, 각 단계마다 **정답과 비교하는 테스트를 먼저** 만들고 진행합니다.

1. **날짜 기둥(일주)** — 60개 글자 조합이 날마다 하나씩 돌아가는 순환 계산
2. **시간 기둥(시주)** — 시계 시각이 아니라 **실제 해의 위치**로 시각을 고쳐서 계산 (→ [계산 조사 쉬운 버전](./2026-09-13-saju-core-calculation-research.easy.md))
3. **월·연 기둥** — 사주의 한 해는 1월 1일이 아니라 **입춘**(2월 초)에 시작
4. **음력 입력** — 음력 생일을 양력으로 바꿔서 계산
5. (나중) **대운/세운** — 10년 단위·1년 단위 운의 흐름

## 6. 풀이는 어떻게 만들어?

### 통째로 해석하면 안 되는 이유

8글자 전체 조합마다 풀이를 쓰려면, 기둥 4개만 해도 60 × 60 × 60 × 60 ≈ **1,290만 가지**입니다. 사람이 다 쓸 수 없어요.

### 그래서: 조각으로 나눠서 조립

> 🏣 **비유: 레고 블록**
> 1,290만 개의 완성품을 미리 만들어 두는 대신, **블록 50~100개**를 만들어 두고 사람마다 맞는 블록을 골라 조립합니다.

경우의 수가 작은 기준(축)으로 쪼갭니다.

| 기준 | 경우의 수 | 알려주는 것 |
|------|-----------|-------------|
| 일간 | 10 | 성격의 뿌리 |
| 십성 | 10 | 재물·관계·직업 성향 |
| 오행 분포 | 5종 × (많음/적당/부족) | 기운의 균형 |
| 신강/신약 | 몇 가지 | 내 기운의 세기 |

이 블록들을 주제별로 조합합니다.

| 보여줄 주제 | 쓰는 블록 |
|-------------|-----------|
| 성격 | 일간 + 신강약 + 오행 균형 |
| 재물 | 재성(돈과 관련된 십성) + 오행 |
| 애정 | 관성·재성 + 일지(태어난 날의 뒷글자) |
| 직업 | 식상 + 관성 |

각 블록은 완성된 문단으로 써두고, "다만 / 한편 / 그리고" 같은 연결어로 이어 붙입니다. 순서는 중요한 것부터(일간 → 오행 → 십성)입니다.

### 나중에는 AI로

엔진이 결과를 **항목별로 정리해서** 내놓기 때문에, 같은 데이터를 나중에 **AI에게 그대로 넘겨** 더 자연스러운 풀이를 쓰게 할 수 있습니다.
지금 블록 조립을 제대로 만들어 두면, AI 풀이로 가는 길이 저절로 열려요.

## 7. 처음 완성할 것 (MVP)

**MVP**(최소 기능 제품)는 "이것만 있으면 서비스라고 부를 수 있는 최소한"입니다.

> **입력 → 사주와 풀이 보기 → 로그인 → 내 사주 저장**

만드는 순서:

| 단계 | 할 일 | 왜 이 순서? |
|------|-------|-------------|
| 0 | 저장소 뼈대 만들기 (web + api + core) | 집부터 지어야 가구를 들인다 |
| 1 | 엔진: 8글자 계산 + 정답 비교 테스트 | 모든 것의 기초 |
| 2 | 엔진: 오행·십성·신강약 | 풀이 재료 |
| 3 | 엔진: 풀이 블록 + 조립기 | 화면에 보여줄 글 |
| 4 | 서버(NestJS): 계산·풀이 요청 창구 | NestJS 첫 실습 |
| 5 | 웹: 입력 화면 → 서버 호출 → 결과 화면. **로그인 없이도 체험 가능** | 여기서 처음 눈으로 확인 |
| 6 | 데이터 창고 + 로그인 + 내 사주 저장 | 가장 복잡해서 맨 뒤 |

> 💡 **로그인을 맨 뒤에 두는 이유**: 로그인은 복잡합니다. 처음부터 하면 핵심(계산)을 만들기도 전에 지칩니다.

## 8. 그다음엔?

같은 기반 위에 하나씩 얹습니다.

대운/세운 → 오늘의 운세(매일, 알림·앱) → 궁합 → **AI 사주 상담** → 유료 리포트

모바일 앱은 **Expo**(모바일 앱 제작 도구)로 만들고, 계산기(core)는 그대로 재사용합니다.

## 10. 아직 안 정한 것

- GraphQL로 바꿀 시점 (익숙해진 뒤)
- 로그인 세부 방식 (출입증을 언제 다시 발급할지, 카카오·구글 로그인 후 돌아오는 과정)
- 태어난 곳 경도를 어떻게 입력받을지
- 대운/세운, 궁합, 매일 알림, 결제
- AI 풀이에 어떤 지시문(프롬프트)을 줄지

---

## 11. 주의할 점

- 블록 조립 풀이는 **일반적인 참고용**입니다. 사주는 학파마다 해석이 다르고, 전문가가 사람마다 깊이 보는 상담과는 다릅니다.
- 그래서 서비스에 **"재미/참고용"** 이라는 안내를 붙입니다.
- 블록이 독립적이라, 나중에 전문가 감수나 AI로 **블록 하나씩 따로** 개선할 수 있습니다.

## 정한 것 한눈에

| 정한 것 | 이유 | 고려했다가 뺀 것 |
|---------|------|------------------|
| 수직 슬라이스로 개발 | 전체 구조를 일찍 익힘 | 층별 개발 — 끝까지 아무것도 안 돌아감 |
| 모노레포 (한 저장소) | 계산기를 웹·서버·앱이 함께 씀 | 저장소 분리 — 코드 공유가 번거로움 |
| 엔진 직접 구현 | 공부 목적 + 정확도 직접 통제 | 사주 라이브러리 통째로 사용 — 막히면 그때 전환 |
| REST | 단순해서 처음 배우기 좋음 | GraphQL — 나중에 |
| 계산 결과는 저장 안 함 | 계산 방식 고쳐도 낡은 결과가 안 남음 | 결과 저장 |
| 풀이는 블록 조립 | 1,290만 가지를 다 쓸 수 없음 | 통째 해석 |
| 로그인은 맨 뒤 | 초반 복잡도를 낮춤 | — |

| 사주팔자 | 태어난 연·월·일·시 4개 기둥 × 2글자 = 8글자 |
| 기둥(주, 柱) | 연주·월주·일주·시주. 각각 천간 1글자 + 지지 1글자 |
| 천간 | 기둥의 윗글자. 갑을병정무기경신임계 10개 |
| 지지 | 기둥의 아랫글자. 자축인묘진사오미신유술해 12개 |
| 일간 | 일주의 윗글자. 사주에서 "나 자신" |
| 일지 | 일주의 아랫글자 |
| 오행 | 목(나무)·화(불)·토(흙)·금(쇠)·수(물) 다섯 기운 |
| 십성 | 다른 글자가 "나(일간)"와 맺는 관계 10종류 (재성·관성·식상 등) |
| 신강/신약 | 내 기운이 센 편 / 약한 편 |
| 대운/세운 | 10년 단위 운 / 1년 단위 운 |
| 입춘 | 2월 초의 절기. 사주에서 한 해가 바뀌는 날 |
| 수직 슬라이스 | 기능을 적게, 대신 화면부터 DB까지 끝까지 관통하게 만드는 방식 |
| 모노레포 | 여러 앱을 한 저장소에서 관리하는 방식 |
| Turborepo | 모노레포의 빌드·테스트를 빠르게 돌려주는 도구 |
| 프론트엔드 / 백엔드 | 사람이 보는 화면 / 화면 뒤에서 일하는 서버 |
| NestJS | 서버를 정해진 틀로 짜게 해주는 도구 |
| Next.js | 웹사이트를 만드는 도구 |
| REST | 서버에 데이터를 요청하는 가장 흔한 방식 |
| JWT | 로그인했다는 걸 증명하는 디지털 출입증 |
| PostgreSQL | 데이터베이스(데이터 창고) 종류 |
| Prisma | 데이터베이스를 코드로 편하게 다루는 도구 |
| Docker | 프로그램을 상자에 담아 어디서나 똑같이 켜게 해주는 도구 |
| `DATABASE_URL` | 데이터 창고의 주소. 이것만 바꾸면 창고를 옮길 수 있음 |
| Vitest | 코드가 맞게 동작하는지 자동으로 확인하는 테스트 도구 |
| MVP | 서비스라고 부를 수 있는 최소한의 기능 묶음 |
| 배포 | 만든 것을 인터넷에 올려 누구나 쓰게 하는 것 |
| stale | 원본이 바뀌었는데 옛날 값이 남아 있는 상태 |
