## D1. 일주 기준일(epoch) ✅ 확정

**결정: 별도 epoch 상수를 두지 않고 JDN에서 직접 유도한다.**

```ts
const stemIndex   = (jdn + 9) % 10;   // 0 = 갑
const branchIndex = (jdn + 1) % 12;   // 0 = 자
```

**근거** — JDN 순수 산술과 `korean-lunar-calendar`(KASI 데이터 기반)를 1900-01-01~2050-12-31 **55,152일 전수 대조, 불일치 0**. 원리가 다른 두 방법이 완전히 일치했다. (2026-09-13 검증)

초기에 "1984-02-02 = 갑자일"로 알고 있던 것은 **갑자년과 혼동한 착오**였다. 실제로는 병인일이다.

## D2. 자시 경계 기본값 🔴

**무엇을 정하는가** — 23:00~24:00 출생자의 **일주를 당일로 볼지 다음날로 볼지.**

子시는 23:00~01:00으로 하루를 걸친다. 시지(時支)가 子인 것은 양쪽 모두 같지만, 일주가 갈린다.

| 선택지 | 23:30 출생자의 일주 | 입장 |
|--------|-------------------|------|
| **A. `keep-day`** (야자시 구분) | 당일 유지 | 날짜는 자정에 바뀐다. 23~24시는 "야자시"로 따로 본다 |
| **B. `next-day`** (일괄 변경) | 다음날로 넘김 | 하루의 시작은 子시다. 23시부터 이미 다음날 |

**트레이드오프**
- **정답이 없다.** 명리 유파의 입장 차이이며, 어느 쪽도 "틀렸다"고 말할 수 없다.
- 파급이 크다 — 일주가 바뀌면 **오서둔(五鼠遁)을 통해 시주의 천간까지 연쇄로 바뀐다.** 두 기둥이 동시에 달라진다.
- 하루 24시간 중 1시간, 즉 **전체 사용자의 약 4%** 가 영향을 받는다. 적지 않다.

**권고: B(`next-day`)를 기본값으로, 옵션은 열어둔다.**

```ts
type ZiBoundary = "keep-day" | "next-day";
calculateSaju(birth, { ziBoundary: "next-day" })   // 기본값
```

- 국내 상용 만세력·사주 서비스 다수가 이 방식이다 → 사용자가 다른 서비스와 대조했을 때 어긋나는 일이 적다.
- 로직이 단순하다 — 보정된 진태양시가 23시를 넘으면 날짜를 +1 하고 끝. 예외 분기가 없다.

**반드시 지킬 것**
1. **진태양시 보정(§2.3) 이후에 판정한다.** 순서를 뒤집으면 32분 보정 때문에 23시 전후 출생자가 통째로 틀린다.
2. 결과 화면에 **어떤 기준으로 계산했는지 표기**한다. 다른 서비스와 결과가 달라도 "왜 다른지" 설명이 되고, 이게 곧 신뢰 장치다.
3. D6(시각 미상)과 함께 테스트한다 — 시각을 모르면 이 분기 자체가 성립하지 않는다.

### ✅ 결정: A — `keep-day` (야자시 구분), 2026-09-13

23:00~24:00 출생자는 **당일 일주를 유지**하고, 시지는 子로 본다.

```ts
type ZiBoundary = "keep-day" | "next-day";
calculateSaju(birth, { ziBoundary: "keep-day" })   // 기본값
```

**확정 규칙**

| 출생 시각(진태양시) | 일주 | 시지 | 시간(時干) |
|---|---|---|---|
| 23:00 ~ 23:59 | **당일** | 子 | **당일 일간** 기준 오서둔 |
| 00:00 ~ 00:59 | 당일(자정에 이미 넘어감) | 子 | 당일 일간 기준 오서둔 |

날짜 경계를 자정 하나로만 두므로 **일주 계산에 특별 분기가 없다.** 일주는 달력 날짜에서 그대로 나오고, 자시 여부는 시주에서만 판정한다. D1(JDN 직접 유도)과도 깔끔하게 맞물린다.

**따라오는 책임 — 계산 기준 표기가 더 중요해진다**

국내 상용 서비스 다수는 `next-day` 방식이라, 23~24시 출생자에서 **우리 결과가 타 서비스와 달라진다.** 하루 중 1시간이므로 전체 사용자의 약 4%가 해당한다.

- 결과 화면에 **"야자시 구분 기준으로 계산됨"** 을 반드시 표기한다.
- 해당 시간대 출생자에게는 다른 기준의 결과도 함께 볼 수 있게 하는 것을 검토한다(옵션이 이미 열려 있으므로 비용이 낮다).
- 이 표기는 부가 기능이 아니라 **이 결정을 선택한 이상 필수**다. 없으면 "왜 다른 데랑 다르냐"는 문의가 그대로 신뢰 손상이 된다.

## D3. 음력 변환 라이브러리 🟡

**무엇을 정하는가** — 음력 생일 입력을 양력으로 바꿀 구현체.

**전제**: 한국 음력 ≠ 중국 농력. KST 기준으로 삭(朔)을 판정하므로 **윤달 위치가 다르다.** 중국계 라이브러리(`lunar-javascript` 등)는 사주 기능이 내장돼 편해 보여도 **결과가 어긋나므로 금지**한다.

| 후보 | 범위 | 비고 |
|------|------|------|
| **`korean-lunar-calendar`** (jangjunha) | 1900~2050 동작 확인 | **D1 검증에서 55,152일 전수 일치** — 데이터 무결성 실증됨 |
| `korean_lunar_calendar_js` (usingsky) | 1000~2050 | 범위 최대 |
| `kor-lunar-js` (kahyou22) | 1890~2050 | `isLeapMonth` 옵션 명시 |
| `manseryeok` (yhj1024, TS) | 1391~2100 | TS 네이티브, 사주 기능 포함, 한·중 윤달 차이 보정 명시 |

**권고: `korean-lunar-calendar`.**
D1 검증 과정에서 이미 도입해 **간지 데이터가 55,152일 전수 일치**하는 것을 확인했다. 검증 없이 고른 후보가 아니라 **우리가 직접 측정한 유일한 후보**라는 점이 결정적이다.

**단, 검증한 것은 `getKoreanGapja()`(간지)이지 음↔양 변환이 아니다.** 채택 전 다음을 확인한다.

1. 음↔양 **왕복 변환**이 항등인지 전 범위 자동 테스트 (양력 → 음력 → 양력 = 원본)
2. **윤달 케이스** 별도 대조 — 최근 20년치 윤달을 KASI 값과 맞춰본다
3. 타입 정의 유무 (없으면 `.d.ts` 자체 작성 비용)

`manseryeok`은 범위(1391~2100)와 TS 네이티브가 매력적이므로 **차선책으로 남긴다.** 단 사주 계산 기능은 쓰지 않는다 — 우리 코어가 그걸 하기 때문이고, 유파 옵션(D2)을 우리가 통제해야 한다.

## D4. 지원 연도 범위 🟡

**무엇을 정하는가** — 입력 가능한 생년 범위와 범위 밖 처리.

**제약**: KASI 음양력 데이터 자체가 **2050-12-31에서 끝난다.** 우리 선택이 아니라 원천 데이터의 한계이며, 국내 사주 서비스 전반이 같은 천장을 갖는다.

**권고: 1900-01-01 ~ 2050-12-31.**

- 하한 1900 — 생존자 기준으로 충분하다. 더 내리면 검증 부담만 는다.
- 상한 2050 — 원천 데이터 한계. 우회 불가.
- 범위 밖은 **명확한 에러 메시지**로 거절한다. 조용히 잘못된 값을 내는 것이 최악이다.

```ts
// 나쁜 예: 범위 밖인데 그럴듯한 값이 나옴
// 좋은 예: 지원 범위(1900~2050)를 벗어났음을 명시적으로 알림
```

- 대운(大運)은 10년 단위로 미래를 보므로, **2050에 가까운 생년은 대운 계산이 범위를 넘길 수 있다.** 이 경계 처리를 별도로 정해야 한다. (→ 대운 구현 시)

## D5. 출생지 입력 수준 🔴

**무엇을 정하는가** — 진태양시 보정에 쓸 경도를 어떻게 받을지.

경도는 시주를 직접 바꾼다. 서울(126.98°)과 독도(131.87°)는 약 **20분** 차이이고, 경계에 걸리면 시주가 통째로 달라진다.

| 선택지 | 정확도 | UX 부담 | 구현 |
|--------|--------|---------|------|
| **A. 서울 고정** | 지방 출생자 오차 | 없음 | 최소 |
| **B. 주요 도시 선택** | 실용상 충분 | 드롭다운 1개 | 상수 테이블 |
| **C. 좌표/주소 검색** | 최대 | 높음 | 지오코딩 API 필요 |

**권고: B(주요 도시 선택), 기본값 서울.**

- A는 **조용히 틀린다.** 부산·제주 출생자에게 잘못된 시주를 확신 있게 보여주게 되는데, 사주 서비스에서 이건 신뢰의 문제다.
- C는 Phase 0에 과하다. 외부 API 의존과 개인정보(주소) 수집이 따라온다.
- B는 광역시·도청 소재지 17개 정도면 전국이 20km 내로 커버된다. **상수 테이블 하나로 끝난다.**
- 코어 API는 **경도(number)를 받게** 설계한다. 도시 목록은 web/api 층의 관심사이고, 코어는 경도만 알면 된다. 나중에 C로 올려도 **코어는 그대로다.**

```ts
calculateSaju({ birth, longitude: 126.978, ... })   // 코어는 경도만 안다
```

**해외 출생자**는 Phase 0 범위 밖으로 둔다. tz DB가 처리해주므로 확장 자체는 어렵지 않으나, 도시 목록과 UX가 별개 과제다.

### ✅ 결정: A — 서울 고정, 2026-09-13

Phase 0에서는 출생지를 입력받지 않고 **서울 경도(126.978°)로 고정**한다. 입력 항목을 늘리지 않아 최소 UX로 출시한다.

**단, 코어 API는 경도를 파라미터로 받는다.**

```ts
// 코어는 경도만 안다 — 고정값이라는 사실을 모른다
calculateSaju({ birth, longitude: 126.978, ... })

// 고정은 호출부(web/api)의 상수로 표현한다
export const DEFAULT_LONGITUDE = 126.978;   // 서울
```

고정값을 코어 안에 하드코딩하지 않는 이유는, 나중에 도시 선택이나 좌표 입력으로 올릴 때 **코어를 건드리지 않기 위해서**다. 지금 비용은 인자 하나이고, 이 결정을 뒤집는 비용이 그만큼 낮아진다.

**수용한 트레이드오프 (인지하고 선택함)**

지방 출생자는 경도 오차만큼 진태양시가 틀어지고, 경계에 걸리면 **시주가 달라질 수 있다.**

| 지역 | 서울 대비 경도차 | 시간 오차 |
|---|---|---|
| 제주 | 약 -0.5° | 약 2분 |
| 부산 | 약 +2.1° | 약 8분 |
| 독도 | 약 +4.9° | 약 20분 |

대부분 지역은 10분 이내라 2시간 단위인 시주가 바뀔 확률은 낮지만, **0은 아니다.**

**완화책 (권고)** — 결과 화면에 **"서울 기준으로 계산됨"** 을 표기한다. D2의 계산 기준 표기와 같은 장치이며, 틀릴 수 있다는 사실을 감추지 않는 것이 핵심이다. 지방 출생 문의가 쌓이면 그때 도시 선택(선택지 B)으로 올린다 — 코어 수정 없이 호출부만 바꾸면 된다.

## D6. 출생시각 미상 처리 🔴

**무엇을 정하는가** — 태어난 시각을 모르는 사용자를 어떻게 받을지.

**현실**: 생년월일은 알아도 **시각을 모르는 사용자가 상당수**다. 특히 연령대가 높을수록 그렇다. 이걸 강제 입력으로 막으면 사용자를 잃는다.

| 선택지 | 문제 |
|--------|------|
| A. 시각 필수 | 모르는 사용자가 아무 값이나 넣는다 → **틀린 결과를 확신 있게 제공** |
| B. 정오로 대체 | 위와 같다. 틀렸다는 사실이 감춰진다 |
| **C. 3주(三柱) 모드** | 시주를 빼고 년·월·일주만 — 정직하다 |

**권고: C. 시주를 제외한 3주 모드를 1급 기능으로 지원한다.**

- 시주 없이도 년·월·일주로 **해석의 상당 부분이 성립**한다. 서비스가 성립하지 않는 게 아니다.
- B(정오 대체)가 가장 위험하다. **틀렸다는 사실조차 사용자가 모르게 된다.** A도 사용자가 대충 찍으면 같은 결과가 된다.
- 타입으로 강제한다 — 시각이 optional임이 시그니처에 드러나야 호출부에서 빠뜨릴 수 없다.

```ts
type Birth = {
  date: { year: number; month: number; day: number };
  time?: { hour: number; minute: number };   // 없으면 3주 모드
  longitude: number;
};
type Pillars = {
  year: Pillar; month: Pillar; day: Pillar;
  hour: Pillar | null;                        // 시각 미상이면 null
};
```

**파급**
- 시주에 의존하는 해석 로직(십성·신강약 등)이 **시주 없이도 동작해야 한다.** 나중에 끼워넣기 어려우므로 **처음부터 설계에 넣는다.**
- 결과 화면에 "시각 미상으로 3주만 계산됨"을 명시한다. D2와 같은 신뢰 장치다.
- D2(자시 경계)는 시각을 알 때만 성립한다. 두 옵션의 조합 테스트가 필요하다.

### ✅ 결정: C — 3주(三柱) 모드 지원, 2026-09-13

시각 미상 시 **시주를 제외하고 년·월·일주만 계산**한다. 임의값 대체는 하지 않는다.

```ts
type Birth = {
  date: { year: number; month: number; day: number };
  time?: { hour: number; minute: number };   // 없으면 3주 모드
  longitude: number;
};
type Pillars = {
  year: Pillar; month: Pillar; day: Pillar;
  hour: Pillar | null;                        // 시각 미상이면 null
};
```

**설계 제약 (처음부터 지킬 것)**

- 해석 로직(십성·오행 분포·신강약 등)은 **시주가 `null`이어도 동작해야 한다.** 나중에 끼워넣기 어려우므로 `analysis/`·`interpretation/` 설계 시점부터 전제로 깐다.
- 오행 분포처럼 개수를 세는 로직은 8글자가 아니라 **6글자 기준**이 되므로, 비율 계산의 분모를 상수로 박지 않는다.
- 결과 화면에 **"시각 미상으로 3주만 계산됨"** 을 표기한다 — D2·D5와 같은 신뢰 장치.
- 테스트는 D2와의 **조합**으로 짠다: 시각 있음 × `keep-day` / 시각 없음(자시 분기 미적용). 시각이 없으면 D2 옵션 자체가 무의미해지므로, 그 경우 옵션이 결과에 영향을 주지 않는다는 것을 테스트로 고정한다.

## 확정된 코어 시그니처

D2·D5·D6이 정해지면서 공개 API의 모양이 결정됐다.

```ts
type Birth = {
  date: { year: number; month: number; day: number };
  time?: { hour: number; minute: number };   // D6 — 없으면 3주 모드
  longitude: number;                          // D5 — 호출부가 서울 상수를 넘긴다
};

type Options = {
  ziBoundary?: ZiBoundary;                    // D2 — 기본 "keep-day"
};

function calculateSaju(birth: Birth, options?: Options): Pillars;
```

**남은 것**
- **D4(연도 범위)** — 입력 검증에만 영향. 구현과 병행 가능.
- **D3(음력 라이브러리)** — 음력은 입력 형식일 뿐이고 코어 내부는 양력 하나로 흐른다. 가장 늦게 정해도 파급이 없다.

## 관통하는 원칙 — 계산 기준을 밝힌다

D2·D5·D6은 각각 다른 선택을 했지만 **같은 책임을 남긴다.**

| 결정 | 결과 화면에 표기할 것 |
|------|---------------------|
| D2 `keep-day` | "야자시 구분 기준으로 계산됨" |
| D5 서울 고정 | "서울 기준으로 계산됨" |
| D6 3주 모드 | "시각 미상으로 3주만 계산됨" |

사주는 정답이 하나가 아닌 도메인이고, 우리는 D2에서 국내 다수 서비스와 다른 쪽을, D5에서 정확도를 일부 포기하는 쪽을 택했다.
그래서 **어떤 기준으로 계산했는지 밝히는 것이 선택 사항이 아니라 이 결정들의 필수 짝**이다. 타 서비스와 결과가 달라도 설명이 되고, 그 설명 자체가 제품의 신뢰 장치가 된다.
