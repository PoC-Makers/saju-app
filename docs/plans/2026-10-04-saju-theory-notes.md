사주 이론 가운데 **코드 결과를 바꾸는 지점**을 정리한 문서다. 항목마다 이론, 선택지에 따라 달라지는 결과, 구현 시사점 순서로 적었다.

## 1. 시주와 진태양시 보정

### 이론

시진(時辰)은 하루를 2시간씩 12개로 나눈 단위다. 원래는 **해의 실제 위치**, 즉 태양이 남중하는 시각을 정오로 삼는 시간을 기준으로 한다.
그런데 한국 표준시(KST)는 동경 135° 자오선을 기준으로 정해져 있고, 서울은 약 126.98°E에 있다. 그래서 서울에서는 표준시 정오보다 **약 32분 늦게** 해가 남중한다.

```
경도 차   = 135° − 126.978° ≈ 8.02°
시간 차   = 8.02° × 4분/° ≈ 32분   (지구는 1°를 4분에 돈다)
```

여기에 **균시차(Equation of Time)** 가 더해진다. 균시차는 지구 공전 궤도가 타원이고 자전축이 기울어 있어서 생기는 차이로, **날짜에 따라 약 −14분에서 +16분까지** 달라진다.

| 보정 수준 | 계산 | 특징 |
|---|---|---|
| 보정 없음 | 시계 시각을 그대로 사용 | 국내 많은 서비스의 방식 |
| 경도 보정 (지방평균시) | 표준시 − 약 32분 (서울 기준) | 날짜와 무관하게 일정 |
| 경도 + 균시차 (진태양시) | 지방평균시 + 균시차 | 날짜마다 다르며, 이론상 가장 정확 |

### 결과가 달라지는 예

시진 경계는 홀수 정시다. 예를 들어 미시(未時)는 13:00에 시작한다. 경계 직후의 시각은 보정 여부에 따라 시진이 바뀐다.

```
가상 예시: 시계 시각 13:20 (서울, 甲일 또는 己일 출생)
  보정 없음  → 13:20 → 미시(未) → 시주 辛未
  경도 보정  → 약 12:48 → 오시(午) → 시주 庚午
```

**경계에서 ±30분 안쪽(경도만 보정하면 정확히 32분 안쪽)** 에 태어난 사람은 보정 여부에 따라 시주가 바뀐다. 시진 하나가 2시간이므로 전체 출생 시각의 상당 부분이 여기에 해당한다.

### 구현 시사점

- 진태양시 보정은 **별도 유틸 함수로 분리**한다. 시주 계산과 시각 보정은 서로 다른 관심사다.
- "KST − 32분"으로 고정하면 근사치일 뿐이다. 표준자오선이 시대마다 바뀌었고(§3) 균시차도 빠져 있기 때문이다. #23의 결론대로 **UTC 절대시각 + 실제 경도 + 균시차**로 계산한다.
  ```
  진태양시 = UTC + (경도 / 15)시간 + 균시차(날짜)
  ```
- 보정 방식은 **사용자가 고를 수 있게 하거나 서비스 정책으로 고정**하고, 어느 쪽이든 **결과 화면에 계산 기준을 표기**한다.

## 2. 자시(子時) 경계

### 이론

자시는 23:00부터 01:00까지로, **날짜가 바뀌는 자정에 걸쳐 있는 유일한 시진**이다. 그래서 23시대에 태어난 사람의 **일주를 오늘로 볼지 내일로 볼지**를 두고 학파가 나뉜다.

| 학파 | 23:00~24:00 출생 | 00:00~01:00 출생 |
|---|---|---|
| **자시 통합** (구분 없음) | 23시부터 다음 날로 본다 → **다음 날 일주** | 다음 날 일주 |
| **야자시·조자시 구분** | **야자시(夜子時)**: 아직 오늘 → **당일 일주 유지** | **조자시(朝子時)**: 이미 다음 날 → 다음 날 일주 |

> ⚠️ **용어 주의**: 23:00~24:00이 **야자시(夜子時, 밤의 자시)** 이고, 00:00~01:00이 **조자시(朝子時, 아침의 자시)** 다. 정리 과정에서 둘을 반대로 적는 실수가 잦으므로 코드 주석과 문서에서 특히 조심한다.

### 결과가 달라지는 예

```
가상 예시: 23:30 출생
  자시 통합          → 일주 = 다음 날 간지
  야자시 구분 (keep-day) → 일주 = 당일 간지
```

이 경계에 걸리면 **일주가 통째로 바뀐다**. 일간(日干)은 사주 풀이에서 '나'에 해당하므로 풀이 전체가 달라진다.

### 추가 쟁점 — 야자시의 시주 천간

야자시를 구분하는 학파 안에서도 23시대 **시주의 천간**을 어느 날 일간으로 정할지 다시 갈린다.

- 다음 날 일간으로 정하는 방식: 자시는 새날의 첫 시진이라는 관점
- 당일 일간으로 정하는 방식

→ **확인 필요.** #23의 D2(keep-day)는 일주만 정했다. 시주 천간 규칙은 명시되어 있는지 확인하고, 없으면 결정을 추가해야 한다.

### 구현 시사점

- 확정 결정: **D2 = keep-day (야자시 구분)**
- #23 조사에 따르면 국내 서비스는 대부분 다음 날 일주 방식이다. 그래서 출생 시각의 약 4%(23시대)에서 결과가 다른 서비스와 다르게 나온다. **결과 화면에 기준을 표기**해야 한다.
- 나중에 정책을 바꿀 수 있도록 자시 규칙을 옵션(enum)으로 받는 구조를 권장한다. 예: `zishi: "keep-day" | "next-day"`

## 3. 한국 표준시의 역사적 변경과 서머타임

### 표준자오선 변경 이력

| 기간 | 표준자오선 | UTC 오프셋 |
|---|---|---|
| 1908 ~ 1911 | 127.5°E | UTC+8:30 |
| 1912 ~ 1954.3 | 135°E | UTC+9:00 |
| 1954.3 ~ 1961.8 | 127.5°E (환원) | UTC+8:30 |
| 1961.8 ~ 현재 | 135°E | UTC+9:00 |

### 서머타임(일광절약시간제) 시행기

| 시행 연도 |
|---|
| 1948 ~ 1951 |
| 1955 ~ 1960 |
| 1987 ~ 1988 |

서머타임 기간에 태어난 사람의 출생 기록은 시계를 1시간 앞당긴 시각이다. **기록된 시각에서 1시간을 빼야** 실제 시각이 된다.

### 결과가 달라지는 예

```
가상 예시: 1987년 여름, 기록상 14:10 출생
  서머타임 미반영 → 14:10 → 미시(未)
  서머타임 반영   → 13:10 → 미시(未), 다만 경계에 가까워진다
  + 진태양시 보정 → 약 12:38 → 오시(午)
```

고령 사용자일수록 이런 보정이 여러 겹 쌓인다. 하나라도 빠뜨리면 시주가 1~2칸 밀린다.

### 구현 시사점

- 연도별 표를 **직접 하드코딩하지 않는다.** 시행 시작일과 종료일이 해마다 달라 실수하기 쉽다.
- **IANA tz DB(`Asia/Seoul`)** 로 벽시계 시각을 UTC로 바꾸면 표준자오선 변경과 서머타임이 함께 처리된다. #23에서 1908년 이후 이력이 모두 들어 있음을 실측으로 확인했다.
- 계산 흐름: `벽시계 시각 → (tz DB) → UTC → (경도 + 균시차) → 진태양시`
- 서머타임 전환일에는 같은 시각이 두 번 있거나(중복) 아예 없는(공백) 경우가 생긴다. 이때의 입력 처리 정책도 정해야 한다.

## 4. 양력·음력 입력과 윤달

### 이론

사주 계산은 내부적으로 **양력(그리고 절기)** 을 기준으로 한다. 음력으로 입력받으면 먼저 양력으로 바꿔야 한다.
음력에는 약 3년에 한 번 **윤달**이 끼어 같은 '음력 ○월 ○일'이 한 해에 두 번 나올 수 있다. 그래서 **윤달 여부를 모르면 날짜가 정해지지 않는다.**

### 구현 시사점

- **입력 첫 단계에서 양력/음력을 구분**해 받는다. (`calendar: "solar" | "lunar"`)
- 음력이면 **윤달 여부(`isLeapMonth`)** 를 함께 받는다.
- **UX 주의**: 많은 사람이 자기가 윤달생인지 모른다. 다음 방안을 검토한다.
  - 입력한 음력 날짜가 그해에 윤달로도 존재할 때만 "윤달인가요?"를 묻는다.
  - "모름"을 고르면 평달 기준으로 계산하고, 윤달일 수 있다고 안내한다.
- **한국 음력 ≠ 중국 농력**: 기준 경도가 달라 윤달 배치와 초하루가 어긋나는 해가 있다. 음력 변환에는 **중국계 라이브러리를 쓰지 않는다** (#23 결론). KASI 기반 데이터를 사용한다.
- 범위: 음력 입력은 #24 범위 밖이며 후속 이슈(D3)에서 다룬다.

## 5. 년·월·일주 계산과 데이터 출처

### 이론

| 기둥 | 경계 기준 | 주의점 |
|---|---|---|
| **년주** | **입춘** (양력 1/1이나 음력 설날이 아님) | 입춘 직전 출생자는 전년도 간지 |
| **월주** | **12절(節)** 의 절입 시각 (입춘·경칩·청명…) | 월 천간은 오호둔(五虎遁)으로 정한다 |
| **일주** | 자정 (자시 정책은 §2) | 60갑자가 끊김 없이 순환 |
| **시주** | 시진 (§1, §6) | 진태양시 보정 여부 |

- **절입 시각은 분 단위까지 필요하다.** 절기 당일에 태어났다면 절입 시각 전후로 월주가 바뀌고, 입춘이라면 년주까지 바뀐다.
- 일주는 기준일을 하나 정하면 일수 차이 mod 60으로 구하는 단순 산술이다. #23에서는 JDN(율리우스 적일)을 바탕으로 직접 유도했고, 1900~2050년 55,152일을 KASI 기반 데이터와 전수 대조해 불일치 0을 확인했다.

### 데이터 출처 — 처음 제안과 확정 결정 비교

| 항목 | 처음 제안 | 저장소 확정 결정 (#23·#24) |
|---|---|---|
| 핵심 엔진 | `lunar-javascript`(6tail)를 내장해 년·월·일주, 절기, 대운 계산 | 간지와 규칙은 **직접 구현** |
| 절기·균시차 | lunar 라이브러리 | **`astronomy-engine`** (태양 황경으로 절기를, 같은 라이브러리로 균시차를 계산) |
| `lunar-javascript` | 핵심 엔진 | **검증용 정답지**로만 사용 (Vitest 대조) |
| KASI API | 매 요청 호출하지 않고 검증·보조용 | 같음 — 검증용 |
| 음력 변환 | lunar 계열 | 중국계 금지, KASI 기반 |

**공통 원칙**
- 서비스 요청마다 외부 API(KASI)를 호출하지 않는다. 지연, 장애, 호출 제한 때문이다.
- 천문 계산은 검증된 라이브러리에 맡기고, 결과는 신뢰할 수 있는 데이터와 대조해 검증한다.

> 참고: `lunar-javascript`는 중국 라이브러리라 절기 시각을 **베이징 시간(UTC+8) 기준**으로 계산하는 것으로 알려져 있다(미확인). 정답지로 쓸 때 시간대를 맞추지 않으면 절입 시각이 1시간 어긋나 보일 수 있으니 대조 테스트에서 확인한다.

## 6. 시주 계산 — 오서둔법

시주의 **지지**는 시진(§1)으로 정하고, **천간**은 그날 **일간**에 따라 정해진다. 계산식이 단순해 라이브러리 없이 직접 구현한다.

### 시진표

| 시진 | 시각 (진태양시 기준) | 시진 | 시각 |
|---|---|---|---|
| 자(子) | 23:00 ~ 01:00 | 오(午) | 11:00 ~ 13:00 |
| 축(丑) | 01:00 ~ 03:00 | 미(未) | 13:00 ~ 15:00 |
| 인(寅) | 03:00 ~ 05:00 | 신(申) | 15:00 ~ 17:00 |
| 묘(卯) | 05:00 ~ 07:00 | 유(酉) | 17:00 ~ 19:00 |
| 진(辰) | 07:00 ~ 09:00 | 술(戌) | 19:00 ~ 21:00 |
| 사(巳) | 09:00 ~ 11:00 | 해(亥) | 21:00 ~ 23:00 |

### 오서둔(五鼠遁) — 일간별 자시 천간

| 일간 | 자시 시주 | 규칙 |
|---|---|---|
| 甲·己 | **甲**子 | |
| 乙·庚 | **丙**子 | |
| 丙·辛 | **戊**子 | 자시 천간에서 한 시진마다 천간이 1씩 증가 |
| 丁·壬 | **庚**子 | |
| 戊·癸 | **壬**子 | |

```
천간 인덱스: 甲0 乙1 丙2 丁3 戊4 己5 庚6 辛7 壬8 癸9
지지 인덱스: 子0 丑1 寅2 … 亥11

시간(時干) = (일간 인덱스 % 5) × 2 + 지지 인덱스   (mod 10)
```

검산: 甲일 미시 → (0 × 2 + 7) mod 10 = 7 → **辛**未 ✓ (§1 예시와 일치)

## 7. 해외 출생자

- 경도와 시간대가 다르므로 진태양시 보정을 **"서울 고정"이 아닌 "임의의 경도 + 임의의 시간대"** 로 일반화해 둔다.
  ```
  입력: 벽시계 시각 + IANA 시간대(예: America/New_York) + 경도
  → tz DB로 UTC 변환 → 경도 + 균시차로 진태양시
  ```
- 확정 결정 **D5**: 출생지는 당분간 서울(126.978°)로 고정한다. 다만 **코어 API는 경도를 인자로 받는다.** 위 일반화와 충돌하지 않으며, 해외 지원은 UI와 입력만 늘리면 된다.
- 남반구 등 다른 반구의 문제(예: 계절 반전에 따른 월주 해석)는 유파 논쟁이 있다. 현재 범위 밖이다.

## 8. 검증 전략

배포 전에 **여러 연도와 날짜 샘플**을 신뢰할 수 있는 데이터와 대조하는 테스트 스크립트를 만든다.

| 테스트 범주 | 샘플 예 | 대조 대상 |
|---|---|---|
| 일주 전수 | 1900~2050 모든 날 | KASI 기반 데이터 (#23 완료) |
| 입춘·절기 경계 | 절입 시각 ±1분 | `astronomy-engine` vs `lunar-javascript`(시간대 맞춤) vs KASI |
| 자시 경계 | 22:59 / 23:00 / 23:59 / 00:00 / 00:59 | 정책(D2)에 따른 기대값 |
| 시진 경계 + 진태양시 | 각 홀수 정시 ±35분 | 수동 계산 |
| 표준시 변경기 | 1954.3, 1961.8 전후 | tz DB |
| 서머타임 | 각 시행 연도의 시작·종료일 전후, 중복·공백 시각 | tz DB |
| 음력·윤달 (D3 이후) | 윤달이 있는 해 | KASI |

> 테스트 데이터는 모두 **가상의 날짜와 시각**을 쓴다 (보안 컨벤션: 실제 개인정보 금지).
