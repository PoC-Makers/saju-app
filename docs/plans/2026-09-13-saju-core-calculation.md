# 사주 계산 코어 — 조사와 결정

`packages/core`의 `calendar/`·`pillars/` 설계를 확정하기 위한 조사와, 거기서 나온 결정 기록.
대상은 네 가지: ① 60갑자 순환(일주) ② 진태양시 보정·자시 경계 ③ 절기 기반 월주·입춘 기준 년주 ④ 음력 입력 지원.

## 결론 먼저

- **일주 산식은 확정됐다.** JDN에서 직접 유도하며 별도 기준일 상수가 없다. 55,152일 전수 검증 완료. (→ §1.2)
- **표준시 이력·서머타임은 직접 구현하지 않는다.** IANA tz DB(`Asia/Seoul`)가 전부 갖고 있음을 실측 확인했다. (→ §2.2)
- **진태양시는 "KST − 32분"이 아니다.** UTC 절대시각 + 실제 경도 + 균시차로 계산한다. 표준자오선이 시대별로 바뀌었기 때문. (→ §2.1)
- **절기는 천문 계산(태양황경)이 필요하다** → `astronomy-engine`. 균시차도 같은 라이브러리로 해결된다. (→ §4.3)
- **음력은 KASI 데이터 기반 라이브러리를 쓴다.** 중국 농력과 윤달이 다르므로 중국계 라이브러리 금지. (→ §5.2)

## 결정 현황

| # | 항목 | 결정 | 절 |
|---|------|------|:---:|
| D1 | 일주 기준일(epoch) | ✅ **JDN 직접 유도** (상수 없음) | §1.2 |
| D2 | 자시 경계 | ✅ **`keep-day`** (야자시 구분) | §3 |
| D3 | 음력 변환 라이브러리 | ⬜ 미정 — `korean-lunar-calendar` 유력 | §5.3 |

## 1. 60갑자 순환과 일주

### 1.1 구조

천간 10 × 지지 12 → 최소공배수 60주기. 짝수-짝수/홀수-홀수만 결합하므로 120이 아닌 60이다.

```
천간(天干) 갑을병정무기경신임계          index % 10
지지(地支) 자축인묘진사오미신유술해       index % 12
간지(干支) index 0 = 갑자 … 59 = 계해
```

년·월·시주는 규칙으로 유도되지만(→ §4.4), **일주만은 유도 규칙이 없다.** 끊김 없이 흘러온 순환이라 경과일수로만 구한다.

### 1.2 ✅ D1 — 일주 산식 확정 (2026-09-13)

**별도 epoch 상수를 두지 않고 JDN에서 직접 유도한다.**

```ts
const stemIndex   = (jdn + 9) % 10;   // 0 = 갑
const branchIndex = (jdn + 1) % 12;   // 0 = 자
```

**검증 경위**

처음에 "1984-02-02 = 갑자일"과 "1900-01-01 = 갑술일"이 2일 어긋나 보였으나, **전자가 착오였다.**
1984년은 갑자**년**(60년 주기의 시작)이지 갑자**일**이 아니다. 실제 1984-02-02는 **병인일**이다.
년주 앵커와 일주 앵커를 혼동한 것으로, 사주 자료에서 흔한 함정이다.

**전수 대조 결과**

| 항목 | 값 |
|------|-----|
| 방법 A | JDN 순수 산술 (위 식) |
| 방법 B | `korean-lunar-calendar` (KASI 천문데이터 기반) `getKoreanGapja()` |
| 대조 범위 | 1900-01-01 ~ 2050-12-31 |
| 대조 일수 | **55,152일** |
| 불일치 | **0일** |

원리가 다른 두 방법(순수 산술 vs KASI 데이터 테이블)이 150년 전 기간에서 완전히 일치했다.
표준시 전환일(1954-03-21, 1961-08-10)과 서머타임 구간(1955~1960, 1987~1988)도 포함된 범위다.

> **일주는 표준시·서머타임과 무관하다.** 달력상 날짜만으로 결정되므로 §2의 시간 보정이 일주를 바꾸지 않는다.
> D2에서 `keep-day`를 택해 날짜 경계를 자정 하나로 고정했으므로(→ §3), 이 성질이 끝까지 유지된다.

**남은 확인 (선택)**

방법 B가 KASI 데이터 기반이긴 하나 KASI 원본은 아니다. 원한다면 [공공데이터포털 KASI 음양력 API](https://www.data.go.kr/data/15012679/openapi.do)로 최종 확인할 수 있다(`lunIljin` 필드, **서비스키 발급 필요**). 지원 범위는 1391-02-05 ~ 2050-12-31이고, 이 API는 율리우스적일(JDN)도 함께 반환하므로 위 식을 직접 대조하기 좋다.
다만 독립 2개 방법이 55,152일 전수 일치했으므로 **구현을 막는 요소는 아니다.**

> 교훈: 사주 계산에서 "널리 알려진 상수"는 검증 없이 쓰면 안 된다. 다만 이번 건은 자료가 틀린 게 아니라 **년주 앵커를 일주 앵커로 잘못 읽은** 경우였다.

### 1.3 구현 메모

- 날짜 → JDN 변환은 정수 연산으로. `Date` 객체의 로컬 타임존 개입을 차단하기 위해 **UTC 기준**으로만 다룬다.
- `Math.floor` vs `Math.round` — 부동소수점 오차로 하루가 밀리는 사고가 잦다. 정수 나눗셈으로 구현하고 경계일(자정 전후) 테스트를 반드시 넣는다.
- JS의 `%`는 음수에서 음수를 반환한다. `((n % 60) + 60) % 60` 형태를 강제한다.

## 2. 시간 보정 — 진태양시

### 2.1 왜 "KST − 32분"이 틀린가

흔한 구현은 서울 경도(126.978°E)와 표준자오선(135°E) 차이 8.022° × 4분 = **약 32분**을 일괄로 뺀다. 두 가지가 빠져 있다.

**(a) 표준자오선이 시대별로 바뀌었다.** 32분은 현재(135°)에만 맞는 값이다.

**(b) 균시차(Equation of Time)가 빠졌다.** 지구 공전궤도의 이심률과 자전축 기울기 때문에 진태양시는 평균태양시 대비 **−14분 ~ +16분** 진동한다. 연중 최대 30분 폭이므로 시주(2시간 단위)의 경계를 넘길 수 있다.

### 2.2 한국 표준시 이력 (실측 검증 완료)

Node 22의 `Intl`(IANA tz DB)로 `Asia/Seoul`의 과거 오프셋을 직접 조회한 결과:

| 날짜 | tz DB 오프셋 | 해석 |
|------|-------------|------|
| 1910-06-01 | **+08:30** | 대한제국 표준시 (127.5°) |
| 1930-06-01 | +09:00 | 일제강점기, 일본 표준시 (135°) |
| 1958-06-01 | **+09:30** | 8:30 표준시 **+ 서머타임 1h** |
| 1960-06-01 | **+09:30** | 〃 |
| 1962-06-01 | +09:00 | 1961-08-10 이후 135° 복귀 |
| 1987-08-01 | **+10:00** | 9:00 + 서머타임 1h (서울올림픽 대비) |
| 1988-08-01 | **+10:00** | 〃 |
| 1990-08-01 | +09:00 | 서머타임 폐지 |
| 2026-09-13 | +09:00 | 현재 |

주요 전환점: 1954-03-21 → UTC+08:30(127.5°) / 1961-08-10 → UTC+09:00(135°) 복귀.
서머타임 시행기: **1948~1951, 1955~1960, 1987~1988.**

> **→ tz DB가 표준시 변경과 서머타임을 모두 정확히 담고 있다. 직접 테이블을 만들지 않는다.**
> 손으로 만든 표는 반드시 어딘가 틀리고, tzdata는 전 세계가 검증한다.

### 2.3 계산 파이프라인

```
입력: 생년월일시(로컬 벽시계) + 출생지 경도
  │
  ├─ ① 벽시계 → UTC 절대시각      ... tz DB (Asia/Seoul). 표준시 변경·서머타임 자동 처리
  │
  ├─ ② UTC → 평균태양시           ... UTC + (경도 ÷ 15)시간
  │
  ├─ ③ 평균태양시 → 진태양시       ... + 균시차(EoT)
  │
  └─ ④ 진태양시 → 시지(時支)       ... 2시간 단위 구간
```

**핵심: ②가 경도를 직접 쓰므로 표준자오선이 몇 도였는지 알 필요가 없다.** 시대별 분기 없이 한 식으로 모든 연도가 처리된다. 1958년생이든 2026년생이든 같은 코드가 맞는 답을 낸다.

균시차는 `astronomy-engine`으로 구한다(→ §4.3). 별도 근사식(Spencer 등)을 쓰면 정밀도 관리 부담만 생긴다.

### 2.4 ✅ D5 — 출생지 입력: 서울 고정 (2026-09-13)

**Phase 0에서는 출생지를 입력받지 않고 서울 경도(126.978°)로 고정한다.** 입력 항목을 늘리지 않아 최소 UX로 출시한다.

> 조사 단계 권고는 "주요 도시 선택(드롭다운)"이었다. 출시 속도를 우선해 **더 단순한 쪽으로 결정**했고, 아래 트레이드오프를 인지하고 수용했다.

**단, 코어 API는 경도를 파라미터로 받는다.**

```ts
// 코어는 경도만 안다 — 고정값이라는 사실을 모른다
calculateSaju({ birth, longitude: 126.978, ... })

// 고정은 호출부(web/api)의 상수로 표현한다
export const DEFAULT_LONGITUDE = 126.978;   // 서울
```

고정값을 코어 안에 하드코딩하지 않는 이유는, 나중에 도시 선택이나 좌표 입력으로 올릴 때 **코어를 건드리지 않기 위해서**다. 지금 비용은 인자 하나이고, 이 결정을 뒤집는 비용이 그만큼 낮아진다.

**수용한 트레이드오프**

지방 출생자는 경도 오차만큼 진태양시가 틀어지고, 경계에 걸리면 **시주가 달라질 수 있다.**

| 지역 | 서울 대비 경도차 | 시간 오차 |
|---|---|---|
| 제주 | 약 −0.5° | 약 2분 |
| 부산 | 약 +2.1° | 약 8분 |
| 독도 | 약 +4.9° | 약 20분 |

대부분 지역은 10분 이내라 2시간 단위인 시주가 바뀔 확률은 낮지만, **0은 아니다.**

**완화책** — 결과 화면에 **"서울 기준으로 계산됨"** 을 표기한다(→ §8). 지방 출생 문의가 쌓이면 그때 도시 선택으로 올린다 — 광역시·도청 소재지 17개면 전국이 20km 내로 커버되고, **코어 수정 없이 호출부만 바꾸면 된다.**

**해외 출생자**는 Phase 0 범위 밖이다. tz DB가 처리해주므로 확장 자체는 어렵지 않으나, 도시 목록과 UX가 별개 과제다.

## 3. ✅ D2 — 자시 경계: `keep-day` (2026-09-13)

### 3.1 무엇이 갈리는가

子시는 23:00~01:00으로 **하루를 걸친다.** 시지가 子인 것은 어느 쪽이든 같지만, 23:00~24:00 출생자의 **일주**가 갈린다.

| 선택지 | 23:30 출생자의 일주 | 입장 |
|--------|-------------------|------|
| **A. `keep-day`** (야자시 구분) | 당일 유지 | 날짜는 자정에 바뀐다. 23~24시는 "야자시"로 따로 본다 |
| B. `next-day` (일괄 변경) | 다음날로 넘김 | 하루의 시작은 子시다. 23시부터 이미 다음날 |

**정답이 없다. 명리 유파의 입장 차이이며 어느 쪽도 "틀렸다"고 말할 수 없다.**

### 3.2 결정: A — `keep-day`

```ts
type ZiBoundary = "keep-day" | "next-day";
calculateSaju(birth, { ziBoundary: "keep-day" })   // 기본값
```

**확정 규칙**

| 출생 시각(진태양시) | 일주 | 시지 | 시간(時干) |
|---|---|---|---|
| 23:00 ~ 23:59 | **당일** | 子 | **당일 일간** 기준 오서둔 |
| 00:00 ~ 00:59 | 당일(자정에 이미 넘어감) | 子 | 당일 일간 기준 오서둔 |

날짜 경계를 자정 하나로만 두므로 **일주 계산에 특별 분기가 없다.** 일주는 달력 날짜에서 그대로 나오고, 자시 여부는 시주에서만 판정한다. D1(JDN 직접 유도)과 깔끔하게 맞물린다.

> 조사 단계 권고는 B(`next-day`)였다 — 국내 상용 서비스 다수가 그 방식이기 때문. **반대로 결정했으므로 아래 표기 책임이 따라온다.**

### 3.3 반드시 지킬 것

1. **진태양시 보정(§2.3) 이후에 판정한다.** 순서를 뒤집으면 32분 보정 때문에 23시 전후 출생자가 통째로 틀린다.
2. **결과 화면에 "야자시 구분 기준으로 계산됨"을 표기한다.** 국내 다수 서비스는 `next-day`라 23~24시 출생자(전체의 약 4%)에서 **우리 결과가 타 서비스와 달라진다.** 이 표기는 부가 기능이 아니라 이 결정을 택한 이상 **필수**다. 없으면 "왜 다른 데랑 다르냐"는 문의가 그대로 신뢰 손상이 된다.
3. 해당 시간대 출생자에게 다른 기준의 결과도 함께 보여주는 것을 검토한다 — 옵션이 이미 열려 있어 비용이 낮다.
4. **파급 주의** — 일주가 바뀌면 오서둔(五鼠遁)을 통해 **시주의 천간까지 연쇄로 바뀐다.** 두 기둥이 동시에 달라지므로 테스트에서 함께 검증한다.
5. D6(시각 미상)과 조합해 테스트한다 — 시각을 모르면 이 분기 자체가 성립하지 않는다.

## 4. 절기 기반 월주 · 입춘 기준 년주

### 4.1 사주의 한 해는 1월 1일에 시작하지 않는다

년주는 **입춘(立春)** 을 기점으로 바뀐다. 1월 1일도, 음력 설도 아니다.

- 2026년 2월 3일생 → 아직 **2025년(을사)** 의 년주
- 2026년 2월 5일생 → **2026년(병오)** 의 년주

입춘은 매년 2월 3~5일 사이에서 움직이므로 **날짜 하드코딩이 불가능하다.** 반드시 계산해야 한다.

### 4.2 12절(節)이 월의 경계다

24절기 중 **절(節)** 12개만 월 경계로 쓴다. (중기(中氣) 12개는 쓰지 않는다.)

| 절기 | 태양황경 | 시작되는 월지 |
|------|---------|--------------|
| 입춘 | 315° | 寅(인) |
| 경칩 | 345° | 卯(묘) |
| 청명 | 15° | 辰(진) |
| 입하 | 45° | 巳(사) |
| 망종 | 75° | 午(오) |
| 소서 | 105° | 未(미) |
| 입추 | 135° | 申(신) |
| 백로 | 165° | 酉(유) |
| 한로 | 195° | 戌(술) |
| 입동 | 225° | 亥(해) |
| 대설 | 255° | 子(자) |
| 소한 | 285° | 丑(축) |

월지가 寅부터 시작하는 것이 **인월세수(寅月歲首)** — 년주 교체점이 입춘인 이유와 같은 뿌리다.

### 4.3 절기 계산 — `astronomy-engine`

절기 = 태양의 겉보기 황경이 15°의 배수에 도달하는 순간. 천문 계산이 필수다.

- **`astronomy-engine`** (npm, MIT, cosinekitty)
  - `SearchSunLongitude(targetLon, startTime, limitDays)` — 임의 황경 도달 시각을 직접 검색. 절기 계산에 그대로 맞는 API.
  - VSOP87 / NOVAS C 3.1 기반, 정밀도 **±1 arcmin**. 절기 시각 오차는 분 단위 이내로 충분하다.
  - 의존성 없는 순수 JS/TS → `packages/core`의 "프레임워크 독립" 원칙에 부합.
  - **균시차(§2.3 ③)도 같은 라이브러리로 해결** → 의존성 하나로 절기 + EoT 동시 커버. **채택 권고.**
- `suncalc`는 가볍지만 황경 정밀 검색 API가 없다. 부적합.
- 절기 시각은 계산 비용이 있으므로 **연 단위로 캐시**한다 (한 해 12개 값).

### 4.4 월간(月干)·시간(時干)은 규칙으로 유도

지지가 정해지면 천간은 표로 결정된다. 계산이 아니라 매핑이다.

**월간 — 오호둔(五虎遁): 년간 → 인월의 천간**

| 년간 | 인(寅)월의 천간 |
|------|----------------|
| 갑·기 | 병인 |
| 을·경 | 무인 |
| 병·신 | 경인 |
| 정·임 | 임인 |
| 무·계 | 갑인 |

**시간 — 오서둔(五鼠遁): 일간 → 자시의 천간**

| 일간 | 자(子)시의 천간 |
|------|----------------|
| 갑·기 | 갑자 |
| 을·경 | 병자 |
| 병·신 | 무자 |
| 정·임 | 경자 |
| 무·계 | 임자 |

> 시간이 **일간**에서 유도된다는 점이 중요하다. 자시 선택(§3)이 일주를 바꾸면 시주까지 연쇄로 바뀐다 — 두 옵션은 독립이 아니다.

## 5. 음력 입력 지원

### 5.1 왜 필요한가

어르신 세대는 생일을 음력으로 기억하는 경우가 많다. 음력 입력은 **국내 사주 서비스의 사실상 필수 기능**이다.

### 5.2 한국 음력 ≠ 중국 농력

둘 다 삭망월 기반이지만 **기준 경도가 다르다.** 한국은 KST 기준으로 삭(朔)과 절기 시각을 판정하므로, 경계에 걸리면 **날짜가 하루 어긋나거나 윤달 위치가 달라진다.**

> **중국계 라이브러리(`lunar-javascript` 등)를 쓰면 안 된다.** 사주 계산 기능이 내장되어 편해 보이지만 중국 시간 기준이라 한국 사주와 결과가 어긋난다.

### 5.3 ⬜ D3 — 라이브러리 선정 (미정)

| 후보 | 지원 범위 | 비고 |
|-----------|----------|------|
| **`korean-lunar-calendar`** (jangjunha) | 1900~2050 동작 확인 | **D1 검증에서 55,152일 전수 일치** — 데이터 무결성 실증됨 |
| `korean_lunar_calendar_js` (usingsky) | 1000~2050 | 범위 최대 |
| `kor-lunar-js` (kahyou22) | 1890~2050 | `isLeapMonth` 옵션 명시 |
| `manseryeok` (yhj1024, TS) | 1391~2100 | TS 네이티브, 사주 기능 포함, 한·중 윤달 차이 보정 명시 |

**유력: `korean-lunar-calendar`.** D1 검증 과정에서 이미 도입해 간지 데이터가 전수 일치하는 것을 확인했다. 검증 없이 고른 후보가 아니라 **우리가 직접 측정한 유일한 후보**라는 점이 결정적이다.

**단, 검증한 것은 `getKoreanGapja()`(간지)이지 음↔양 변환이 아니다.** 채택 전 확인할 것:

1. 음↔양 **왕복 변환**이 항등인지 전 범위 자동 테스트 (양력 → 음력 → 양력 = 원본)
2. **윤달 케이스** 별도 대조 — 최근 20년치 윤달을 KASI 값과 맞춰본다
3. 타입 정의 유무 (없으면 `.d.ts` 자체 작성 비용)

`manseryeok`은 범위(1391~2100)와 TS 네이티브가 매력적이라 **차선책으로 남긴다.** 단 내장 사주 계산 기능은 쓰지 않는다 — 우리 코어가 그걸 하고, 유파 옵션(§3)을 우리가 통제해야 하기 때문이다.

### 5.4 윤달(閏月) 처리

음력 입력은 `(연, 월, 일)` 3개로 부족하다. **윤달 여부 플래그가 반드시 있어야 한다.**

```ts
type LunarDate = { year: number; month: number; day: number; isLeapMonth: boolean };
```

- UI에서 해당 연도에 윤달이 없으면 체크박스를 비활성화한다.
- 음력은 **입력 형식일 뿐**이다. 받는 즉시 양력으로 변환하고, 코어 내부는 양력 하나로만 흐른다. 음력이 파이프라인 안쪽까지 들어오면 복잡도가 폭발한다.

## 6. 입력 모델

### 6.1 ✅ D6 — 출생시각 미상: 3주(三柱) 모드 (2026-09-13)

**현실**: 생년월일은 알아도 **시각을 모르는 사용자가 상당수**다. 특히 연령대가 높을수록 그렇다. 강제 입력으로 막으면 사용자를 잃는다.

| 선택지 | 문제 |
|--------|------|
| 시각 필수 | 모르는 사용자가 아무 값이나 넣는다 → **틀린 결과를 확신 있게 제공** |
| 정오로 대체 | 위와 같고, **틀렸다는 사실조차 감춰진다** — 가장 위험 |
| **3주 모드** ✅ | 시주를 빼고 년·월·일주만 — 정직하다 |

**결정: 시각 미상 시 시주를 제외하고 년·월·일주만 계산한다. 임의값 대체는 하지 않는다.**
시주 없이도 년·월·일주로 해석의 상당 부분이 성립한다. 서비스가 성립하지 않는 게 아니다.

```ts
type Birth = {
  date: { year: number; month: number; day: number };
  time?: { hour: number; minute: number };   // 없으면 3주 모드
  longitude: number;
};
type Pillars = {
  year: Pillar; month: Pillar; day: Pillar;
  hour: Pillar | null;                        // 시각 미상이면 null
};
```

**설계 제약 (처음부터 지킬 것)**

- 해석 로직(십성·오행 분포·신강약 등)은 **시주가 `null`이어도 동작해야 한다.** 나중에 끼워넣기 어려우므로 `analysis/`·`interpretation/` 설계 시점부터 전제로 깐다.
- 오행 분포처럼 개수를 세는 로직은 8글자가 아니라 **6글자 기준**이 되므로, 비율 계산의 분모를 상수로 박지 않는다.
- 결과 화면에 **"시각 미상으로 3주만 계산됨"** 을 표기한다(→ §8).
- 테스트는 §3과 **조합**으로 짠다: 시각 있음 × `keep-day` / 시각 없음. 시각이 없으면 자시 옵션이 무의미해지므로, **그 경우 옵션이 결과에 영향을 주지 않는다**는 것을 테스트로 고정한다.

### 6.2 ⬜ D4 — 지원 연도 범위 (미정)

**제약**: KASI 음양력 데이터 자체가 **2050-12-31에서 끝난다.** 우리 선택이 아니라 원천 데이터의 한계이며, 국내 사주 서비스 전반이 같은 천장을 갖는다.

**제안: 1900-01-01 ~ 2050-12-31.**

- 하한 1900 — 생존자 기준으로 충분하다. 더 내리면 검증 부담만 는다.
- 상한 2050 — 원천 데이터 한계. 우회 불가.
- 범위 밖은 **명확한 에러로 거절한다.** 조용히 잘못된 값을 내는 것이 최악이다.
- **대운(大運)은 10년 단위로 미래를 보므로, 2050에 가까운 생년은 대운 계산이 범위를 넘길 수 있다.** 이 경계 처리는 대운 구현 시 별도로 정한다.

## 7. 코어 시그니처와 폴더 매핑

D2·D5·D6이 정해지면서 공개 API의 모양이 결정됐다.

```ts
type Birth = {
  date: { year: number; month: number; day: number };
  time?: { hour: number; minute: number };   // D6 — 없으면 3주 모드
  longitude: number;                          // D5 — 호출부가 서울 상수를 넘긴다
};

type Options = {
  ziBoundary?: ZiBoundary;                    // D2 — 기본 "keep-day"
};

function calculateSaju(birth: Birth, options?: Options): Pillars;
```

```
[입력] 생년월일시 · 양/음력 · 경도
   │
   ├─ (음력이면) 양력 변환                    calendar/lunar.ts
   ├─ 벽시계 → UTC (tz DB)                    calendar/timezone.ts
   ├─ UTC + 경도 + 균시차 → 진태양시            calendar/true-solar-time.ts
   ├─ 절기 시각 계산 (태양황경)                 calendar/solar-terms.ts
   │
   ├─ 년주 ← 입춘 기준                         pillars/year-pillar.ts
   ├─ 월주 ← 12절 + 오호둔                     pillars/month-pillar.ts
   ├─ 일주 ← JDN 직접 유도                     pillars/day-pillar.ts
   └─ 시주 ← 진태양시 + 오서둔(일간 의존)        pillars/hour-pillar.ts
```

`docs/conventions/filesystem.md`의 `packages/core` 구조와 그대로 맞는다. 새 폴더는 필요 없다.

### 의존성 추가 예정

| 패키지 | 용도 | 상태 |
|--------|------|------|
| `astronomy-engine` | 절기(태양황경) + 균시차 | 채택 권고 |
| 음력 변환 (§5.3) | 음↔양 변환 | **미정** — 대조 테스트 후 결정 |

tz DB는 **런타임 내장**이라 의존성 추가가 없다. 단 Node 빌드에 full-icu가 포함되어야 한다(Node 13+ 기본 포함).

## 8. 관통하는 원칙 — 계산 기준을 밝힌다

D2·D5·D6은 각각 다른 성격의 결정이지만 **같은 책임을 남긴다.**

| 결정 | 결과 화면에 표기할 것 |
|------|---------------------|
| D2 `keep-day` | "야자시 구분 기준으로 계산됨" |
| D5 서울 고정 | "서울 기준으로 계산됨" |
| D6 3주 모드 | "시각 미상으로 3주만 계산됨" |

사주는 정답이 하나가 아닌 도메인이고, 우리는 D2에서 국내 다수 서비스와 다른 쪽을, D5에서 정확도를 일부 포기하는 쪽을 택했다.
그래서 **어떤 기준으로 계산했는지 밝히는 것은 선택 사항이 아니라 이 결정들의 필수 짝**이다. 타 서비스와 결과가 달라도 설명이 되고, 그 설명 자체가 제품의 신뢰 장치가 된다.

## 9. 검증 전략

사주 계산은 **틀려도 화면에 그럴듯하게 나온다.** 눈으로는 검증이 안 되므로 외부 정답지가 필수다.

1. **KASI 만세력을 정답지로** — 일진·절기·음양력 변환을 직접 대조한다.
2. **경계값 위주 테스트** — 일반 케이스는 대충 짜도 맞는다. 틀리는 건 항상 경계다.
   - 입춘 전후 (년주 교체)
   - 각 절기 전후 (월주 교체)
   - 23:00~01:00 (자시 — §3의 `keep-day` 규칙)
   - 진태양시 보정으로 시주가 넘어가는 케이스
   - 서머타임 시행기(1955~1960, 1987~1988) 출생
   - 표준시 전환일(1954-03-21, 1961-08-10) 전후
   - 윤달 생일
   - 시각 미상 × 자시 옵션 조합 (§6.1)
3. 위 케이스를 **KASI 값과 함께 픽스처로 고정**한다. 리팩터링 시 회귀 방지.
