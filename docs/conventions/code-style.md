# 코드 스타일 컨벤션

코드를 쓸 때 **처음부터 따르는 기본 원칙**이다. 문제가 생긴 뒤에 찾아보는 참고서가 아니라, 설계와 구현의 출발점으로 삼는다.

핵심 문장에는 표식을 붙인다 — **[필수]** 예외 없이 지킨다 · **[금지]** 하지 않는다 · **[주의]** 놓치기 쉬운 함정. 표식이 붙은 문장만 따라 읽어도 규칙 전체가 잡히도록 유지한다.

> 작성 중인 문서다. 확정된 내용부터 채워 넣는다 — 추가 예정: 네이밍 · enum 패턴 · 주석 · import 순서 · 포맷(Prettier)·린트(ESLint).

## 세 가지 원칙 — 우선순위: KISS > YAGNI > DRY

KISS(단순하게), YAGNI(필요할 때 만들기), DRY(중복 줄이기)는 유명한 원칙이지만, 그대로 두면 서로 부딪힌다. 중복을 없애려다 코드가 복잡해지고(DRY vs KISS), 나중을 대비해 공통화하다 안 쓸 코드를 만든다(DRY vs YAGNI). 그래서 각 원칙에 **판단 기준**을 붙이고, 부딪힐 때의 **우선순위**를 정해 둔다.

**[필수]** 원칙이 부딪히면 **KISS > YAGNI > DRY** 순서로 따르고, 헷갈리면 중복을 남기는 쪽을 택한다. 이렇게 둔 이유는 하나다. **중복은 나중에 합치면 되지만, 잘못 만든 공통 로직은 되돌리기 어렵다** — 이미 여러 곳이 그것에 기대고 있기 때문이다.

### KISS — 스스로 만든 복잡함을 없앤다

"짧게 쓰라"는 뜻이 아니다. **처음 보는 사람이 읽고 바로 고칠 수 있게 쓰라**는 뜻이다. 짧지만 재주 부린 코드가 길고 평범한 코드보다 나쁠 수 있다.

복잡함에는 두 종류가 있고, 대응이 다르다:

| 종류 | 예 | 대응 |
|------|-----|------|
| **문제 자체가 복잡한 것** | 절기 경계, 자시 처리, 진태양시 보정 — 사주 도메인이 원래 이렇다 | 없앨 수 없다. **이름을 붙여 겉으로 드러낸다** |
| **우리가 만들어낸 복잡함** | 필요 없는 추상화, 재주 부린 한 줄, 겹겹의 감싸기 | **KISS가 없애려는 대상.** 만들지 않는다 |

실천 규칙:

- **[필수]** **위에서 아래로 읽히게 쓴다.** 한 함수 안에서는 비슷한 수준의 일만 다룬다 — 큰 흐름을 말하는 함수에 좌표 계산 같은 세부가 섞이면, 읽는 사람은 매번 수준을 오르내려야 한다.

  ```ts
  // ✅ 함수 이름만 따라 읽어도 처리 순서가 보인다
  function calculateSaju(input: BirthInput) {
    const solarTime = toTrueSolarTime(input.date, input.longitude);
    const pillars   = buildFourPillars(solarTime);
    const elements  = analyzeFiveElements(pillars);
    return { pillars, elements };
  }
  ```

- **[금지]** **매직 넘버.** 숫자·문자 값에는 도메인 이름을 붙인다. 이때 **값 자체의 의미는 `const` 상수**로, **값을 가지고 판단하는 규칙은 함수**로 표현한다 — 상수는 "이 값이 무엇인가"에, 함수는 "이 값으로 무엇을 판정하는가"에 답한다.

  ```ts
  // ❌ 숫자만 있으면 아무것도 설명하지 않는다
  const offset = (135 - 127.5) * 4;
  if (hour >= 23 || hour < 1) { ... }

  // ✅ 값의 의미는 const 상수로
  const KST_MERIDIAN = 135;         // 한국 표준시 기준 경도
  const SEOUL_LONGITUDE = 127.5;
  const MINUTES_PER_DEGREE = 4;     // 경도 1도당 시차(분)
  const offset = (KST_MERIDIAN - SEOUL_LONGITUDE) * MINUTES_PER_DEGREE;

  // ✅ 값으로 판단하는 규칙은 함수로
  if (isZiHour(hour)) { ... }       // 자시(子時): 23시~1시
  ```

- **동작이 이름에 드러나면 좋고, 이름 뒤에 숨으면 나쁘다.** `elements.filter(isFire)`처럼 무엇을 하는지 이름만으로 보이면 좋은 코드다. 반대로 헬퍼를 몇 겹씩 감싸서 실제로 무슨 일이 일어나는지 따라가기 어렵게 만들었다면, 겉보기에 깔끔해도 나쁜 코드다.
- **[필수]** **함수를 쪼개는 건 쪼갠 조각에 도메인 이름이 붙을 때만 한다.** `toTrueSolarTime`처럼 이름이 자연스럽게 나오면 좋은 분리다. `processData`, `handleStep2`처럼 이름이 억지스러우면 경계를 잘못 그은 것이니 나누지 말고 구조를 다시 본다. 파일과 호출만 늘어나는 분리는 오히려 복잡함을 더한다.

**판별 질문:** "6개월 뒤의 내가 이 코드를 읽고 바로 고칠 수 있는가?"

### YAGNI — 아직 쓰지 않는 기능은 만들지 않는다

**[금지]** "나중에 필요할 것 같아서" 기능을 만드는 것. 그 예감은 대부분 빗나가고, 빗나간 코드는 지워지지 않은 채 짐이 된다.

**[주의]** 단, YAGNI는 **기능**에 적용하는 원칙이지 **구조**에 적용하는 원칙이 아니다. 확장을 전혀 고려하지 않고 짜면 나중에 전체 설계를 뒤집게 된다. 기준은 **나중에 넣을 때의 비용**이다:

| 나중에 넣는 비용이 | 지금 할까 | 예 |
|------------------|----------|-----|
| **싸다** — 그때 추가해도 됨 | ❌ 만들지 않는다 | 옵션 파라미터, 설정값, 새 함수, 새 필드 |
| **비싸다** — 전체를 뒤집어야 함 | ✅ 구조만 미리 열어둔다 | 데이터 모델의 기본 형태, 모듈 경계, 의존 방향, 공개 API의 형태 |

> 한 줄로: **싼 준비는 미리 해두고, 비싼 결정은 두 번째 사례가 나올 때 한다.**
> 실제 적용 — core는 사주 전용으로 단순하게 시작하되(YAGNI), 계산 결과 타입은 구조화해 둔다. 나중에 AI 풀이에 그대로 넘길 수 있도록 — 이것이 "비싼 것을 미리 열어둔" 예다.

### DRY — 중복 제거는 목표가 아니다

DRY는 "같은 코드를 두 번 쓰지 마라"가 아니다. 원래 뜻은 **하나의 규칙(지식)은 코드에서도 한 곳에만 존재해야 한다**는 것이다. 그래서 판단할 것은 코드의 생김새가 아니라 **출처**다:

- **[주의]** **겉이 같아도 출처가 다르면 다른 코드다.** 사주 풀이 포맷과 토정비결 풀이 포맷이 지금은 똑같아 보여도, 서로 다른 규칙에서 나왔다면 언젠가 따로 바뀐다. 이걸 공통화하면 나중에 분기(`if (type === ...)`)가 덕지덕지 붙은 함수가 된다.
- **판별 질문:** "이 둘은 같은 이유로 함께 바뀌는가?" — 그렇다면 공통화하고, 아니라면 중복인 채로 둔다.
- **[필수]** **세 번 반복될 때 합친다** (Rule of Three). 두 번째 중복은 참는다 — 두 개만으로는 공통 구조가 무엇인지 아직 보이지 않는다.
- **[필수]** **헷갈리면 중복을 택한다.** 중복은 나중에 합치면 그만이지만, 잘못된 공통화는 걷어내기 훨씬 비싸다.
- **[필수]** **남기기로 한 중복에는 표시를 남긴다.** 나중에 읽는 사람과 AI 모두 "판단하고 남긴 중복"과 "아직 못 합친 중복"을 구별할 수 있어야 한다. 겹치는 곳과 합치지 않은 이유를 한 줄로 적는다:

  ```ts
  // [의도된 중복] core/saju/format.ts formatSaju와 겹침 — 토정비결은 다른 규칙이라 따로 바뀐다
  ```

- **[필수]** **판단이 어려우면 사람에게 묻는다.** 특히 AI가 구현 중 "같은 지식인지" 확신이 서지 않으면, 임의로 공통화하거나 말없이 중복을 만들지 말고 사용자에게 물어 함께 결정한다.

### 원칙이 부딪힐 때

**[필수]** 아래 표대로 결정한다:

| 충돌 | 결정 |
|------|------|
| DRY vs KISS — 공통화하면 코드가 복잡해진다 | **KISS를 따른다.** 중복을 남기고 `[의도된 중복]` 표시를 남긴다 |
| DRY vs YAGNI — 나중에 쓸 것 같아 미리 공통화하고 싶다 | **YAGNI를 따른다.** 세 번째 사례가 나올 때 합친다 |
| KISS vs YAGNI — 단순하게 가려면 지금 구조를 잡아야 한다 | **비용으로 판단한다.** 나중에 바꾸기 싸면 미루고, 비싸면 지금 잡는다 |

## 조건식에 이름 붙이기

조건식도 매직 넘버와 같다 — `hour >= 23 || hour < 1`만 있으면 의도를 알 수 없다. 조건에는 이름을 붙이되, **변수와 함수 중 무엇으로 붙일지**는 다음 기준으로 정한다.

**[필수]** **기본은 변수다.** 정의가 쓰는 곳 바로 위에 보이고, 디버깅할 때 값이 그대로 찍히고, 호출을 따라갈 필요가 없다.

```ts
const isZiHour = hour >= 23 || hour < 1;
if (isZiHour) { day = nextDay(day); }
```

**[필수]** 다음 중 하나에 해당하면 **함수**로 뽑는다:

| 신호 | 이유 |
|------|------|
| ① 두 곳 이상에서 쓴다 | 변수는 선언된 범위를 벗어날 수 없다 |
| ② 검사할 값이 바뀐다 | 변수는 한 값에 대한 결과일 뿐이다 |
| ③ 도메인 규칙이다 | 규칙이 바뀔 때 한 곳만 고치면 되게, 규칙은 한 곳에 둔다 |
| ④ 그 조건만 따로 테스트하고 싶다 | 변수는 단독으로 테스트할 수 없다 |

**규칙은 함수로, 그 자리의 의미는 변수로** — 이 조합이 가장 읽기 좋은 경우가 많다. 함수는 "이게 무엇인가"에, 변수는 "그래서 여기서 어떻게 하는가"에 답한다:

```ts
export const isZiHour = (hour: number) => hour >= 23 || hour < 1;  // 규칙: 자시란 23시~1시

const shouldRollToNextDay = isZiHour(hour);                        // 이 맥락: 그래서 날짜를 넘긴다
if (shouldRollToNextDay) { ... }
```

주의할 것:

- **[주의]** **변수는 선언한 그 자리에서 바로 계산된다.** 뒤의 조건이 거짓이라 결과가 쓰이지 않아도 이미 실행된 뒤다. 계산 비용이 크거나 부수 효과가 있는 조건은 함수로 만들어 필요할 때만 호출되게 한다.
- **[주의]** `cond1`, `flag`처럼 **이름이 지어지지 않으면** 변수냐 함수냐의 문제가 아니다. 조건을 잘못 묶었다는 신호이니, 조건 자체를 다시 나눠 본다.

## 타입 정의

### interface에 `I` 접두사를 붙이지 않는다

**[금지]** interface 이름의 `I` 접두사 (`IUser` ❌ → `User` ✅). C#·Java에서 넘어온 관례인데, TypeScript에서는 타입을 가져다 쓰는 쪽에서 그것이 interface로 만들어졌는지 type으로 만들어졌는지 알 수 없고, 알 필요도 없다. 정의하는 쪽의 내부 사정을 이름에 새기면 정보 없는 글자가 하나 늘고, 나중에 정의 방식을 바꾸면 이름이 거짓말이 된다.

### type 기본, interface는 세 경우만

**[필수]** 타입 선언은 **type을 기본**으로 한다. 객체 모양, 유니온, 별칭, 튜플 전부.

```ts
type User = { name: string; age: number };
type FiveElement = "목" | "화" | "토" | "금" | "수";
type UserId = string;
```

**[필수]** interface는 아래 세 경우에만 쓴다. 뒤집어 말하면, 코드에서 interface가 보이면 셋 중 하나라는 **신호**다:

| 경우 | 이유 |
|------|------|
| ① 클래스에 규약을 줄 때 (`implements`) | 약속(규약)과 실제 구현을 나누는 용도 |
| ② 외부 라이브러리 타입을 확장할 때 | 같은 이름을 재선언하면 자동으로 합쳐지는 성질(선언 병합)은 interface만 가진다 |
| ③ 객체를 계층으로 확장할 때 (권장) | `extends`는 속성 충돌을 선언한 그 줄에서 에러로 잡아준다 |

**[주의]** **겹치는 속성이 있을 수 있는 객체를 `&`로 합치지 않는다.** 속성 타입이 충돌해도 `&`는 에러를 내지 않고, 만족시킬 값이 없는 타입(`never`)을 조용히 만든다. 문제는 정의한 곳이 아니라 멀리 떨어진 사용처에서 알아보기 힘든 에러로 터진다. 계층 확장이 필요하면 ③의 interface `extends`를 쓴다.

```ts
type Base = { prop: string };

// ❌ 에러 없이 통과 — prop은 string이면서 number, 즉 never
type Bad = Base & { prop: number };

// ✅ 충돌을 선언한 이 줄에서 바로 알려준다 (컴파일 에러)
interface Good extends Base { prop: number }
```

> type을 기본으로 둔 이유 — 사주 도메인은 유니온·리터럴 조합이 주력이라 type을 안 쓸 수 없고, "기본은 type" 하나면 선언할 때마다 고르는 판단이 사라진다(KISS). 앱 코드 안에서 선언 병합이 조용히 일어나는 사고도 함께 차단된다.
