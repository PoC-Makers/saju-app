# 학습 흐름 정리 (Learning Recap)

프로젝트를 **공부하며 만드는 과정**에서 **배운 것 자체**를 남기는 스킬.
커밋 히스토리가 "코드가 어떻게 바뀌었나"라면, 이 문서는 **"내가 무엇을 이해했고 어디서 막혔나"**를 남긴다.

기준 톤은 **인수인계 가이드 스타일** — 처음 보는 사람도 따라 읽을 수 있게 **쉬운 설명 → 점진 심화**, 비유·예시·콜아웃·표를 적극 사용.

## 가장 중요한 원칙 — 학습 내용을 얇게 쓰지 말 것

이 문서의 **목적은 공부**다. "무엇을 했다"는 회고보다 **"그게 무엇이고 왜 그런가"**가 본문의 중심이어야 한다.

- **§2 배운 개념이 문서의 절반 이상**을 차지해야 한다. 다른 섹션은 그 맥락을 붙여주는 역할이다.
- 개념은 **한 줄 요약으로 끝내지 말고**, 나중에 이 문서만 읽고도 이해되도록 **원리·동작·비교·예시**까지 적는다.
  - 나쁨: "rebase는 커밋을 복사해 다시 얹는다."
  - 좋음: 무엇을 하는지 → 전후 상태를 도식으로 → 무엇이 보존되고 무엇이 바뀌는지 → 언제 쓰고 언제 위험한지
- **대화에서 설명했던 내용을 압축해 버리지 않는다.** 표·도식·예시가 있었다면 문서에도 살린다.
- 개념끼리 헷갈리는 지점이 있으면 **비교표**를 반드시 넣는다 (예: refactor vs perf, classic vs ruleset).
- 분량을 아끼지 않는다. 짧아서 나중에 다시 검색해야 하는 문서가 가장 나쁘다.

## 언제 쓰나

- 사용자가 명시적으로 요청: "학습 기록 정리", "이번 단계 회고", "지금까지 배운 것 문서로"
- 한 단계(예: Step 0 모노레포 뼈대)를 끝냈을 때 → "이번 단계 학습 기록 남길까요?"라고 **먼저 제안**하고 확정 후 작성

## 무엇을 담나 (대화에서 수집)

이번 회차의 대화를 훑어 아래를 뽑는다. **꾸며내지 말고 실제로 오간 내용만.**

1. **한 일** — 이번 세션/단계에서 실제로 달성한 것 (짧게)
2. **배운 개념** ★ **본문의 중심** — 이번에 설명한 개념 전부. 개념마다:
   - 쉬운 정의 → 동작 원리(도식·코드·명령) → 헷갈리는 개념과의 비교표 → 언제 쓰나/주의점
   - 진짜 헷갈릴 만한 것에만 비유 콜아웃, 꼭 기억할 한 줄엔 핵심 콜아웃
3. **따라한 과정** — 단계별로, 각 단계에 **왜 했는지**를 붙여서
4. **막힌 지점 & 질문 (Q&A)** ★ — 사용자가 헷갈려하거나 물어본 것을 **질문 원문 그대로 → 그때 이해한 답**으로.
   답에는 **왜 헷갈렸는지**와 **그 답이 이후 결정을 어떻게 바꿨는지**까지 적는다.
5. **내린 결정** — 정한 것 + 이유 + **제쳐둔 대안과 그 이유**
6. **새 용어** — 이번에 처음 나온 용어를 한 줄로 (사전 역할)
7. **다음 단계** — 이어서 할 일, 미정으로 남은 것

> 이번 회차에 없는 섹션은 통째로 뺀다. 억지로 채우지 않는다. 단, §2는 거의 항상 있어야 한다.

## 정리 구조 (권장 섹션 순서)

`template.html`의 순서를 그대로 따른다:

```
표지 → 인트로("이 기록은?") → 1.한눈에 → 2.배운 개념 → 3.따라한 과정(단계별)
→ 4.막힌 지점 & 질문(Q&A) → 5.내린 결정 → 6.새 용어 → 7.다음 단계 → 푸터
```

## 톤·양식 규칙 (기준 문서 준수)

- **쉬운 말 먼저, 전문용어는 그 다음.** 초보가 읽어도 이해되게.
- **비유 콜아웃**(`callout analogy`, 🏣)으로 개념을 일상에 빗대기. 남발 금지 — 진짜 헷갈릴 만한 개념에만.
- **핵심 콜아웃**(`callout key`, 💡)으로 꼭 기억할 한 줄.
- **예시 콜아웃**(`callout example`, 초록 점선)으로 구체 시나리오/명령 예.
- **표**로 용어·결정·비교를 압축.
- **단계는 원형 번호 뱃지**(`ol.steps`)로, 각 단계에 "왜 했는지(why)"를 붙인다.
- **Q&A 블록**은 질문을 미화하지 말고 사용자가 실제로 물은 톤 그대로.
- **식별자·명령은 monospace**(`<code>`, `<pre>`), 상태 변화는 `<pre>` 도식으로.
- **솔직하게** — 아직 안 정한 것/확인 못 한 것은 그대로 "미정"·"확인 중"이라 적는다.
- 이모지는 기준 문서처럼 마커로만 소량(💡 🏣). 과용 금지.

## 만드는 절차

1. **출력 폴더 준비**: `docs/recaps/` (없으면 생성)
2. **HTML 작성**: `template.html`의 CSS·구조를 그대로 쓰고 내용을 채운다.
   저장: `docs/recaps/{YYYY-MM-DD}-{desc}.html` (desc는 영문 kebab-case)
3. **HTML을 브라우저로 열어 확인** — `open`으로 열고 렌더링(한글 폰트·표·콜아웃)을 확인한다.
4. **PDF 변환은 물어본 뒤** — 자동으로 만들지 않는다. "PDF로도 만들까요?"라고 확인하고, 원할 때만 변환한다:
   ```bash
   HTML="$HOME/workspace/saju-app/docs/recaps/{YYYY-MM-DD}-{desc}.html"
   OUT="${HTML%.html}.pdf"
   CHROME=""
   for c in \
     "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
     "/Applications/Google Chrome Canary.app/Contents/MacOS/Google Chrome Canary" \
     "/Applications/Chromium.app/Contents/MacOS/Chromium"; do
     [ -x "$c" ] && CHROME="$c" && break
   done
   "$CHROME" --headless=new --disable-gpu --no-pdf-header-footer \
     --print-to-pdf="$OUT" "file://$HTML"
   ```
   변환했으면 `qlmanage -t -s 1400 -o <임시폴더> "$OUT"`로 썸네일을 만들어 렌더링을 눈으로 확인한다.
5. **결과 안내**: 생성된 경로를 알려준다.

## 파일 규칙

| 항목 | 규칙 |
|------|------|
| 출력 폴더 | `docs/recaps/` |
| 파일명 | `{YYYY-MM-DD}-{desc}.html` (예: `2026-08-26-git-convention.html`) |
| 원본(SoT) | HTML. PDF는 요청 시에만, 언제든 재생성 가능 |
| 커밋 | **개인화 문서라 `docs/recaps/`째로 gitignore** — 추적 안 함 |

- [ ] 헷갈리는 개념쌍에 비교표를 넣었는가
- [ ] 실제 대화 내용만 담았는가 (지어낸 것 없음)
